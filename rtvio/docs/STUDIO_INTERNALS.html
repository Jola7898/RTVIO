RTVIO Studio Internals

RTVIO Studio is a single desktop process that remote-controls an Android phone as a camera, records every frame of each take to disk, queues each take for VGGT reconstruction on the GPU, and shows the finished point cloud and Poisson mesh in the browser. This document explains how each part works, from the bytes on the wire to the meshing parameters, together with every library, model and tool the system depends on.

§1System topology

Three programs are involved. The first is the Android app (rtvioapk), which only captures and transmits. The second is the Studio process (python -m rtvio.studio), which owns the phone socket, the session files, the job queue and the web server. The third is one reconstruction subprocess per job (python -m rtvio.vggt_reconstruct), which holds the GPU while it runs and exits when the job is done.

§2The Studio process

Studio.__init__ in server.py starts everything in this order: it creates data/sessions/ and data/video_jobs/, deep-merges studio_settings.json over DEFAULT_SETTINGS, starts the GPU sampler, the job queue and the phone listener, and records the LAN IPv4 addresses. To find the default-route address, it connect()s a UDP socket to 10.255.255.255, which sends no packet. The startup log prints these addresses so the operator knows what to type into the phone.

Everything runs on standard-library threads, and nothing is asynchronous:

Settings persist in rtvio/data/studio_settings.json. Each POST /api/settings sends a partial patch (for example {"recon":{"overlap":12}}). The server merges the patch recursively and writes the whole file back.

§3Phone link & wire protocol

One TCP stream carries everything, multiplexed by a leading header byte. All fields are big-endian. The canonical definition is Protocol.kt, with the Python twin in stream/protocol.py. Every read goes through recv_exact() because recv(n) can return fewer than n bytes: a 200 KB JPEG always arrives in pieces over WiFi. Two limits reject a desynchronised stream: MAX_JPEG_BYTES (32 MB) and MAX_IMU_BATCH (4096).

3.2 Version negotiation

The app reads the greeting with a 1.5 s timeout. Greeting ≥ 2 means remote control: the app connects armed (camera preview on, nothing recorded) and starts a reader coroutine for COMMAND packets. A v1 greeting, or no greeting at all, gives the original behaviour: stream from the moment of connect and never read another byte. Because of this, live_pipeline.py, vggt_live.py and mock_receiver.py work with the new app unchanged.

3.3 How a take moves

  1. Start. POST /api/record/start → PhoneLink.start_recording(). The desktop refuses unless the phone is connected, is v2, reports armed and no take is open. It then opens a SessionWriter (origin="studio", unconfirmed) and sends {"cmd":"start","session":id, resolution, fps, jpeg_quality, gps, imu}.
  2. Confirm. The phone saves the capture settings into its own preferences, opens a FrameSpool, rebinds the camera if the resolution changed, and reports recording. If no confirmation arrives within 8 s, the take is discarded and its empty directory removed.
  3. Record. Every FRAME goes into the phone's spool, then onto the socket, then into frames/NNNNNN.jpg. IMU and GPS rows accumulate in memory. The phone's own REC button works too: a STATUS for an unknown session id opens a take with origin="phone".
  4. Stop. stop_recording() sends STOP. If the socket is down, STOP is re-sent every 2 s while the phone still reports recording. The phone closes the camera gate and switches to finishing.
  5. Finalize. Once the spool and encoder are empty, the phone reports armed with last_completed and last_frames_sent. SessionWriter.finalize() writes the JSON sidecars and compares the frame count the phone says it sent with the count received. If auto_reconstruct is on, the session is submitted to the queue.

3.4 Why frames are written inline

A ~100 KB write to a local SSD takes well under a millisecond. Writing on the socket thread means no in-process queue can overflow and silently drop frames. If the disk is slow, TCP backpressure slows the phone, and the phone spools to flash instead of dropping. stream/recorder.py deliberately makes the opposite trade (a bounded queue that drops), because it serves a live pipeline that must never stall.

ConstantValueEffect
START_CONFIRM_TIMEOUT_S8 sAn unconfirmed START is discarded
RESUME_GRACE_S120 sA phone that drops mid-take may reconnect and keep uploading into the same take
SOCKET_IDLE_TIMEOUT_S15 sA v2 phone sends STATUS every second, so 15 s of silence means the link is dead
STOP_RESEND_S2 sRetry interval for a STOP that was lost with a dying socket
LEGACY_IDLE_FINALIZE_S3 sA v1 app's automatic take ends this long after frames stop

3.5 Clock pinning

Frames and GPS use the wall clock (epoch ms). IMU samples use SensorEvent.timestamp: nanoseconds since boot, on a monotonic clock that doesn't jump when NTP corrects the time. Every STATUS carries wall_ms and elapsed_ns read back to back on the phone, so SessionWriter computes boot_to_wall = wall_ms/1e3 − elapsed_ns/1e9 for each STATUS. At finalize it takes the median to convert IMU rows onto the frames' timeline. This is more precise than the receive-time minimum filter stream/clock.py falls back on, because transport delay never enters the calculation.

3.6 Offline sessions and transfer

RECORD LOCALLY writes the same layout to Android/data/com.rtvio.mapper/files/recordings/<id>/ with no socket involved. Later, Saved sessions → Transfer opens a dedicated connection, ignores the greeting, and sends SESSION_BEGIN(id, file_count, total_bytes), then one SESSION_FILE(rel_path, size) header plus raw bytes per file in 64 KB chunks, then SESSION_END. _receive_session_transfer streams each file to disk in chunks of up to 1 MB. _normalize_transferred_meta then rewrites the app's session_meta.json into the Studio format, so the session list does not break on the app's different field names.

§5GPU job queue

jobs.ReconQueue is a list of ReconJob objects protected by a lock, plus one worker thread. A job is either "recording" (source = a session directory, output = the next free recon-N/ inside it) or "video" (source = any local file path, output = video_jobs/<name>-<n>/). There are three reasons each job runs as its own subprocess:

  • VGGT already sizes its windows to fill free VRAM, so two concurrent jobs would only compete for memory.
  • When the process exits, every byte of VRAM it held is released, so no fragmentation or cached allocations carry over to the next job.
  • An OOM, a crash or a Cancel (proc.terminate()) kills that job and nothing else.

The last flag makes the job exit when it finishes instead of keeping its viewer open, so the next queued job can start. The environment sets PYTHONUNBUFFERED=1 and PYTHONIOENCODING=utf-8, and stdout and stderr go to job.log. On Windows, CREATE_NO_WINDOW stops a console window from appearing.

Progress channel. The job rewrites progress.json atomically (a .tmp file, then os.replace). On Windows, os.replace fails with PermissionError while a reader has the file open, so it retries 20× at 50 ms. Fields: stage (loading → frames → vggt → fusing → meshing → extras → done|error), fraction (0–0.85 across VGGT windows, then 0.86 / 0.90 / 0.97 / 1.0), window/windows, frames_done, eta_s, vggt_fps, points, faces, error. On an exception, the last reported stage is kept so the UI can say where the job failed.

State. The job list is in memory and is empty again after a Studio restart. The UI still works after a restart because list_sessions() and list_video_jobs() rebuild everything from disk and overlay live job state only where a job is still tracked. Delete refuses queued or running jobs, and deleting a recon removes only its recon-N/, never the captured frames.

§7Browser front end

Three files with no build step: index.html (171 lines), app.js (487), style.css (122). The page polls /api/state every 1 s and /api/sessions and /api/video-jobs every 2.5 s, then re-renders with template strings. Every value interpolated into HTML goes through esc().

  • Viewfinder. An <img src="/api/preview.mjpg">: the browser renders the multipart stream as video, with no script involved. The server waits on a Condition signalled by each new preview or frame, so it doesn't poll.
  • Settings. Every [data-setting="recon.overlap"] control posts a one-key patch when it changes. Re-rendering pauses for 3 s after a local edit so the 1 s poll doesn't overwrite what the user is typing.
  • Session cards. Each card is rendered inside its own try/catch. Before this, one transferred session with an unexpected meta shape threw inside .map() and blanked the whole list.
  • GPU sparkline. A 160×28 canvas plotting 90 one-second nvidia-smi samples as a line with an area fill.
  • 3D viewer. three.js r128 with OrbitControls and PLYLoader, vendored under web/vendor/ so the page works offline. It loads the binary PLYs directly and switches between point cloud (size 1–8 px, no attenuation) and mesh (unlit vertex colours, or shaded MeshStandardMaterial, with optional wireframe). It overlays the camera path from cameras.json and fits near/far planes to the bounding sphere (radius/2000 … radius×200).

§8Reconstruction engine

vggt_reconstruct.py (1,135 lines) turns a frame sequence into cloud_raw.ply and mesh_poisson.ply using vision only: no GPS unless asked for, and no IMU. The per-window body and the finalization tail are the shared functions _process_window and _finalize_and_write, so batch (--video, --from-recording) and live (vggt_live) runs of the same footage produce the same geometry.

  1. Load the model. VGGT(enable_point=False, enable_track=False) drops about 98 M parameters of unused heads. Weights come from data/models/vggt1b_model.pt (or $RTVIO_VGGT_CHECKPOINT) via torch.load(mmap=True, weights_only=True), so the 5 GB file is never copied into RAM, with from_pretrained("facebook/VGGT-1B") as the network fallback. The aggregator (~909 M params, nearly all the compute) is cast to bf16 on compute capability ≥ 8 and fp16 below that. On fp16 cards the heads stay in fp32, because depth_head's exp() confidence overflows 65504 and returns NaN (found on a 4 GB GTX 1650). TF32 is on. cudnn.benchmark is off because it re-tunes for every new tensor shape, which caused 7–11 s stalls on the last window and on DPT remainder chunks.
  2. Prepare frames. FrameLoader decodes on an 8-thread pool and prefetches the next window while the GPU runs the current one. Portrait frames are rotated 90° clockwise to landscape: a 9:16 frame at VGGT's 518 px width would otherwise lose 44% of its height to cropping or spend 43% of its tokens on padding. Frames are resized with INTER_AREA to 518 px wide, the height is rounded to a multiple of 14 (the ViT patch size) and centre-cropped to ≤ 518 px, which gives 518×294 for 16:9 and 518×392 for 4:3. Each frame's blur score (Laplacian variance) is recorded. With masking on, YOLO sets dynamic pixels to 0 under a lock, because ultralytics predictors are not thread-safe.
  3. Size the windows. auto_window_frames fits a linear VRAM model measured on this card: n = (free_MB − 1230·16·Mpix − 1500) / (39·tokens/1000), clamped to 12…64. On OutOfMemoryError the window shrinks by ×0.75 and the same start is retried; this is safe because state is only mutated after the forward pass succeeds. _plan_next merges a leftover tail shorter than half a window into the last window.
  4. Forward pass. The aggregator runs under autocast, then camera_head → pose_encoding_to_extri_intri (cam-from-world 3×4 extrinsics plus K), and depth_head (DPT, run in 16-frame chunks) → per-pixel depth and confidence.
  5. Per-pixel geometry and gates (GPU). Pixels are unprojected to world points P (S,H,W,3). A pixel is kept only if it passes all of these gates:
    • Confidence gate: the 50th percentile of pixels above the window's floor value. On one overcast aerial clip, 84% of pixels sat exactly at the floor, so a raw percentile kept everything and let a cone of sky depth into the cloud.
    • Continuity mask: relative depth jump > 4% per pixel, dilated 3×3. This removes the "flying pixels" between foreground and background.
    • Validity: depth > 0 and all coordinates finite.
    Normals come from central differences and are oriented toward the observing camera, because Poisson needs oriented normals.
  6. Seam alignment. For the shared frames, pixels valid in both windows become correspondences. With ≥ 2,000 correspondences, fusion.robust_sim3 runs. First it scores 512 minimal 3-point Umeyama hypotheses (solved as one batched SVD) on 20 k points with a 5% relative inlier threshold. Then 10 iterations of Cauchy-weighted IRLS Umeyama refine the best one: w = 1/(1+(r/2σ)²), σ = 1.4826·median, residuals divided by depth so near and far points count equally, at most 250 k points. RANSAC comes first because plain IRLS settled on 0.41 instead of 0.70 when 25% of outliers were biased one way. Below 2,000 correspondences (a whip pan, a blank wall), the fallback chains through one shared camera and takes scale from the median depth ratio, and the report shows a warning.
  7. Voxel fusion. Voxel size = voxel_factor × median_depth / fx, about one pixel's footprint. Only frames not already fused are added. Voxel keys pack three 21-bit indices into one int64; torch.unique + index_add_ reduce on the GPU, and a background numpy thread merges the partial results every 6 windows so the GPU never waits on the merge. Each voxel stores summed position, colour and normal, its point count, and a distinct-frame count; a point seen by only one frame is usually a depth-edge artifact.
  8. Finalize the cloud. Voxels with fewer than min_views frames are dropped, then a statistical outlier filter runs (k = 12, mean + 2σ, the Open3D criterion, on cKDTree with all cores). The output frame is either relative (first camera at the origin, rotation undone via R_UNROTATE, OpenCV → Y-up via diag(1,−1,−1)) or ENU metres if georeferenced. cloud_raw.ply is binary little-endian with xyz, normals, RGB and a views scalar; cameras.json holds per-frame R, centre and K in the same frame.
  9. Mesh. pymeshlab Screened Poisson with depth 10, samplespernode=1.5, pointweight=4, all threads. Poisson closes surfaces over regions with no data, so faces with any vertex farther than max(3·voxel, 2·octree cell) from an input point are trimmed. Connected components smaller than max(200, 0.2%) of faces are then dropped. Vertex colours come from the nearest cloud point. Output: mesh_poisson.ply. If meshing fails, a warning is logged and the cloud is still complete.
  10. Georeference, extras, report. With --gps-mode global, each camera is paired with its nearest fix within 1 s. With ≥ 3 anchors spanning ≥ 5 m, one global robust_sim3 maps the trajectory to ENU, and the median and 90th-percentile residuals are logged. --extras writes LAS 1.2 (point format 3, UTM via a closed-form Snyder projection, WKT .prj sidecar), OBJ and GLB through trimesh, a COLMAP text model with the exact 518-px frames for gsplat, and when georeferenced a 2.5D DSM PNG with .pgw world file. Every run writes CHECKPOINT_REPORT.md and .json (throughput, peak VRAM, seams, blur, georeferencing) and trajectory_check.png.

§9Live viewer (Watch live)

recon_viz.ReconViz is a small ThreadingTCPServer started inside the job process. It serves one HTML page and a /events Server-Sent Events stream over HTTP/1.0 (no Content-Length, never chunked). Each window pushes four message types: pts (new fused points decimated to 4,000 by linspace, re-centred on the first point pushed because browsers lose float precision at UTM scale), frame (the last frame of the window as a base64 JPEG), window (fps, keep %, seam scale and residual, blur), and at the end report. When the report arrives the page fetches /mesh.ply (falling back to /cloud.ply) and switches from the growing preview to an explorable view.

It is a preview channel, not part of the data path. Each browser tab has a 200-message queue that drops its oldest message rather than block, so a slow or closed tab cannot affect the reconstruction.

Camera pipeline

Software JPEG limits frame rate (one 4 MP capture ran at ~15 fps), so each frame is split. The analyzer thread copies the planes into one of 4 encoder slots before the ImageProxy closes. Compression then runs on 2 threads, and a single emitter thread waits on the futures in submission order, so frames arrive in capture order. When all four slots are busy, the frame is skipped and counted in skippedCount. Frames are timestamped at sensor exposure, converted to wall-clock time, rather than after encoding. The AE target FPS range is chosen from the ranges the device advertises, preferring a fixed [t,t]. A software gate with 10% tolerance enforces the cap, because without the tolerance normal jitter would reject every other frame.

Encoder

Rotation happens while the planes are copied into NV21, which saves a pass and a second multi-MB buffer. NV21 orders chroma V then U, the reverse of the YUV_420_888 plane order; swapping them turns red to blue. ExposedByteArrayOutputStream hands out its backing array, so there is no per-frame copy for the garbage collector.

Intrinsics

LENS_INTRINSIC_CALIBRATION is in active-array pixels (e.g. 4000×3000), so it is mapped through the same centred crop and scale CameraX uses to fill the buffer, then through the frame rotation. A (0,0) principal point falls back to the image centre. Without a calibration, focal length ÷ sensor size is used; without either, 0.8 × width.

Socket writer priority

On every pass, writeLoop drains in this order:

  1. Control queue: IMU, GPS, STATUS, intrinsics (capacity 512)
  2. Spool: recorded frames, oldest first
  3. Preview slot: latest viewfinder image only
  4. Live video queue: capacity 10, oldest frame evicted when full, polled for 20 ms

The socket uses TCP_NODELAY and a 256 KB send buffer, with a 5 s connect timeout and a 1.5 s greeting timeout. Reconnect backoff doubles up to 60 s. An active recording always reconnects within 2 s, whatever the auto-reconnect setting, because its spool still has to reach the desktop.

FrameSpool

Records are i32 length + packet in a file under filesDir/spool/. When the reader catches up the file is truncated to zero, so it never grows beyond the largest backlog. It refuses writes when free space drops below 300 MB, checked every 32 records (statfs is too slow to call per frame).

IMU & GPS

Accelerometer and gyroscope fire independently. Pairing each accel sample with the latest gyro sample leaves up to 10 ms of staleness, which is 0.9° of error during a 90°/s pan. Instead, accel samples are held until a later gyro sample arrives, and the gyro value is linearly interpolated onto each accel timestamp. Batches flush every 50 ms on an URGENT_AUDIO-priority HandlerThread. GPS uses GPS_PROVIDER only, not fused location, because WiFi and cell positioning give plausible fixes that can be hundreds of metres off.

Build: compileSdk / targetSdk 34, minSdk 24, JDK 17, viewBinding, R8 minify and resource shrinking in release (no signing config committed). The foreground service types (dataSync|camera|location) are declared at runtime, because from Android 14 starting a location-type service without the permission throws, so indoor mode must not request it.

Not used, and why

COLMAP, Open3D, GTSAM, pyproj and rasterio had no Windows wheel for Python 3.13 on this machine when checked. Their functions are implemented directly: Sim(3) alignment, UTM projection, outlier filtering, point-to-mesh distance, plane-sweep stereo, and a .prj sidecar instead of laspy.add_crs(). The earlier LingBot-Map track (it needed FlashInfer under WSL2) was dropped for VGGT on 2026-09-14.

§15Gaps found while reading

These came up while tracing the code for this document. None has been fixed yet.

Security

A Transfer from any device on the LAN can write files outside data/sessions/

The session id and each rel_path come straight from the wire and are passed to os.path.join without validation. An id like ..\..\x, an absolute path, or a file path containing ../ escapes the sessions root. Port 5555 listens on 0.0.0.0 with no authentication. Fix: validate the id against SESSION_ID_RE and realpath-check every destination, the same way the HTTP file routes already do.

Behaviour

Studio's default gps_mode: "off" disables GPS auto-detection

build_command always passes --gps-mode off. reconstruct_from_recording only switches to global automatically when gps_mode is None, so an outdoor take with real fixes stays un-georeferenced unless the user changes the setting. Consider a third option, "auto", that omits the flag.

Offline

Watch live needs internet access

The Studio page vendors three.js, but the recon_viz page loads it from jsDelivr. In the field with no uplink, the live viewer page renders blank. recon_viz also binds 0.0.0.0, while Studio's own UI binds 127.0.0.1.

Accuracy

Georeferencing is still above the ≤ 1 m target

test_georeference_vggt.py's noise sweep shows consumer-grade GPS noise keeps the global Sim(3) above 1 m. RTK or PPK input is the strongest known way to close the gap. None of the four runs in §13 used GPS.

By design

Job history is in memory; the web UI has no authentication

After a restart, job ids, logs and GPU stats for past jobs are gone, while all files remain and stay operable. The control page can start the phone camera and GPU jobs, which is why it binds to localhost by default.
